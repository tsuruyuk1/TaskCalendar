# Отчёт по этапу 3. Локальное хранилище: Room

## Что сделано
- `Task` стал Room-Entity (таблица `tasks`): `id`, `title`, `description`, `date`, `time`, `isDone`.
- `TaskDao`: добавить, обновить, удалить, получить все, получить по дате, получить по id, очистить таблицу.
- `AppDatabase` — наследник `RoomDatabase`, один экземпляр на приложение (singleton, `Room.databaseBuilder`).
- Тестовый экран «Отладка БД» (меню ⋮ на главном экране): добавление, чтение, изменение, удаление; результаты пишутся
  в Logcat (тег `TaskDb`) и показываются на экране.
- Главный экран и экран деталей читают данные из базы. Пустое состояние — если в базе нет задач.
- Все обращения к базе — через корутины в `Dispatchers.IO`.

## Ключевые понятия
| Понятие | Пояснение |
|---|---|
| **Room** | Библиотека-обёртка над SQLite: таблицы описываются Kotlin-классами и аннотациями, SQL-запросы проверяются **при компиляции**, результат сразу превращается в объекты |
| **@Entity** | Класс описывает таблицу; каждое поле — столбец (`tableName = "tasks"` — имя таблицы) |
| **@PrimaryKey(autoGenerate = true)** | Первичный ключ; база сама выдаёт уникальные возрастающие id. При создании объекта передаём `id = 0` — Room понимает, что нужно сгенерировать |
| **@Dao** | Интерфейс с операциями над таблицей; реализацию генерирует Room (через KSP) |
| **@Insert / @Update / @Delete** | Готовые операции по объекту (`@Update`/`@Delete` находят строку по первичному ключу) |
| **@Query** | Собственный SQL, например `SELECT * FROM tasks WHERE date = :date`; `:date` — параметр из аргумента функции |
| **RoomDatabase** | Абстрактный класс: список `entities`, `version` и методы-фабрики DAO |
| **suspend / корутины** | `suspend fun` может «приостанавливаться», не блокируя поток; вызывается только из корутины (`lifecycleScope.launch`) или другой suspend-функции |
| **Dispatchers.IO** | Пул потоков для ввода-вывода. `withContext(Dispatchers.IO) { ... }` выполняет блок там, а затем возвращает выполнение в главный поток, где безопасно менять View |

## Формат даты и времени
Дата хранится строкой `yyyy-MM-dd`, время — `HH:mm`. Такой формат сортируется лексикографически так же, как по календарю,
легко сравнивается в SQL (`WHERE date = '2026-10-05'`) и не зависит от часового пояса/локали. На этапе 6 пригодится для
запросов вида «задачи месяца» (`date BETWEEN ... AND ...`).

## Ответы на вопросы для защиты
**Что будет с данными при закрытии и повторном открытии приложения?**
Они сохранятся. Room пишет данные в файл SQLite (`/data/data/ru.university.taskcalendar/databases/task_calendar.db`) во
внутреннем хранилище приложения — это постоянная память, а не оперативная. Данные исчезнут только при удалении приложения
или очистке его данных в настройках.

**Почему обращения к БД не в основном потоке?**
Главный (UI) поток отвечает за отрисовку и реакцию на касания. Долгая операция ввода-вывода заморозит интерфейс
(возможен ANR — «приложение не отвечает»). Поэтому запросы выполняются в `Dispatchers.IO`. Room по умолчанию даже
выбрасывает исключение, если запрос выполняется в главном потоке.

**Чем `@Query("SELECT * FROM tasks")` в Room удобнее «чистого» SQL?**
Запрос проверяется на этапе компиляции (опечатка в имени таблицы/столбца — ошибка сборки, а не падение приложения);
результат автоматически преобразуется в `List<Task>` (не нужно вручную читать `Cursor` и сопоставлять столбцы); параметры
подставляются безопасно (`:date`), без ручной склейки строк; поддерживаются `suspend` и `Flow`.

## Как проверить (для скриншота в отчёт)
1. Запустить приложение → меню ⋮ → **Отладка БД** → «Добавить тестовые задачи».
2. Открыть **Logcat**, в фильтре ввести `tag:TaskDb` — в нём будут строки `INSERT`, `SELECT ALL`, `SELECT BY DATE`.
3. Вернуться на главный экран — список показывает записи из базы.
4. Полностью закрыть приложение (смахнуть из списка недавних) и открыть снова — задачи на месте.
5. Сделать скриншоты Logcat и экрана и положить в [`docs/screenshots/`](screenshots/).
